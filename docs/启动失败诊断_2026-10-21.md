# 桥接启动失败诊断（2026-10-21）

给接手 Agent 的处理单。**结论与证据都在这里，未修改任何项目代码。**

后续处理：已按用户授权完成批量身份回填、首次摘要延后及主动重复投递保护；见[有限修复与验证](启动与重复投递有限修复_2026-10-21.md)。下文保留诊断时的状态与建议，不代表修复后已实际重启或生产积压已清空。

## 一、现象

运行 `Start-WeChat-Live.cmd` 后控制台输出：

```
Checked 58 packages in 2ms
Plugin files prepared; existing mode and channel settings preserved. No login or model call.
微信后端身份、版本、测试群绑定检查通过；未发送消息，未调用模型。
Live mode selected. No model call made by this configuration step.
Checked 152 packages in 7ms
Bridge did not start; inspect var/bridge.stderr.log.
```

而 `var/bridge.stderr.log` 与 `var/bridge.stdout.log` **都是 0 字节**。

## 二、结论

**不是崩溃，也不是代码改坏了。桥接进程在 `web.run_app()` 绑定端口之前，被一段同步的重活卡住，启动脚本 15 秒超时后主动放弃了它。**

卡住的位置是：`_summary_loop` → `_application()` → `identities.backfill()`，它遍历全部档案消息，且**每条记录一次独立 SQLite 连接 + 一次提交**。这段代码跑在事件循环里，所以 HTTP 监听器一直没建立。

## 四、完整链条

1. aiohttp 的 `on_startup` 调用 `bridge.start()`，它 `asyncio.create_task(self._summary_loop())`。
2. `_summary_loop` 第一次迭代立即执行；`pending_scopes()` 返回 4 个到期窗口。
3. 对第一个窗口调用 `self._application(message)`：
   - 构造 `Application`，其中 `MemoryIndex.__init__` 会加载索引代际并对较大 JSON 做 `digest`；
   - 然后执行 `self.identities.backfill(scope, app.store.list_records("raw_message"))`。
4. `backfill()` 逐条调用 `observe()`，而 `observe()` 每次自己 `_connect()` 并提交。
   档案规模越大，这里越慢，且全部是**同步阻塞**。
5. 因为跑在事件循环里，`web.run_app` 走不到 `site.start()`，8766 始终没绑定。
6. `scripts/start_wechat.ps1:76-84` 只轮询 15 秒，超时抛 `Bridge did not start`，`finally` 把子进程杀掉。

## 五、为什么日志是空的

aiohttp 的启动横幅 `======== Running on http://127.0.0.1:8766 ========` 是在 **`site.start()` 成功之后**才打印的。
进程从未绑定成功，也没有抛异常，因此 stdout / stderr 都是空的。**空日志不等于没出错。**

## 六、为什么现在才出现

启动开销 ≈ 档案记录数 × 到期窗口数。

- 17:05 那次启动时，待办窗口尚未到期，`_summary_loop` 不会构造 `Application`，所以启动很快。
- 现在档案增长（800 条冷档 + 数百条原始记录），又同时有 4 个到期窗口，这条同步路径从"几秒"变成"数分钟"。

**这是既有的启动顺序缺陷被数据规模放大，不是近期改动引入的。**

近期改动中与启动路径相关的只有三处，均可排除：

| 改动 | 为何不影响 |
|---|---|
| `bridge.py` 注册 `web_search` | `[bridge.web]` 未配置，`_web_tool()` 直接返回 `None` |
| `bridge.py` `start()` 增加 `_ensure_proactive` | `[bridge.proactive]` 为空，`_ensure_proactive` 立即返回 `None` |
| `bridge.py` `receive()` 增加 `is_listening_evidence` 过滤 | 不在启动路径上 |

`bridge.py:280` 的 `identities.backfill(...)` 是原有代码，未被改动。

## 七、修复方案

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 延后第一次摘要** | `bridge.start()` 里在进入 `while` 前先 `await asyncio.sleep(N)`（N 取 10–30 秒），让端口先绑上 | **最小改动**，能立刻恢复可用 |
| **B. 重活移出事件循环** | `_summary_loop` 里把 `_application()` 的同步部分放进 `asyncio.to_thread` | 治本，改动中等 |
| **C. `backfill` 批量化** | `identity.py` 的 `observe()` 改成一个事务批量写，而不是每条一次连接+提交 | 治本，真正把启动时间降下来 |
| **D. 放宽启动超时** | `scripts/start_wechat.ps1` 的 15 秒改大（如 180 秒） | 创可贴，只是别过早放弃 |

**建议 A + C**：A 让服务能起来，C 才真正解决根因。
若只做一个，选 A。

## 八、必须注意

1. **不要删除 `listening_pending` 里的行来"清空积压"**。那是 5 个已冻结的 100 条原文窗口，删了就永久丢失。
   若只想让它先起来，可以把 `next_attempt` 推后，而不是删数据。
2. 修复后需验证：进程能在 15 秒内响应 `/health`，且 `listening_summaries` 开始增长。
3. `listening_summaries` 一直是 0、窗口 100 已第 7 次尝试 → 说明**线上仍跑修复前的旧代码**，
   `4338f6c` 的 split 修复还没生效过。修复启动问题后重启，它才会第一次真正跑起来。
