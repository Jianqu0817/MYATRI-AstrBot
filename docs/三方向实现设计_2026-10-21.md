# 方向 1：自我输出进上下文（1A + 1B）　✅ 已实现

## 1.1 问题定位

"自己的输出进上下文"**原本就已实现**（`src/myatri_bridge/bridge.py` 的 `acknowledge()`：`sent` 确认时写入冷档、`listening_assistant_context`、`recent_messages`）。真正缺失的是**回指**：

```python
# 修改前：只查人类消息表
matches = [m for m in self.short_memory.recent(message.scope)
           if m["sender_id"] == quote["sender_id"] and m["text"] == quote["text"]]
```

`ShortMemory.recent()` 只返回 `listening_messages`（人类消息），而机器人自己的话在 `listening_assistant_context`。因此群友引用机器人原话时匹配必然失败，落到 `unverified_quote_not_original_member_evidence`。

叠加第二个问题：引用机器人**不构成触发条件**，只靠 @ / 关键词 / 10% 随机，所以"你刚才说的不对"有 90% 概率被无视。

## 1.2 设计（已落地）

### 1A 扩展引用解析

新增只读接口：

```
ShortMemory.recent_assistant(scope, limit=200) -> list[dict]
    返回 listening_assistant_context 的 {message_id, text, sender_id, reply_to_id}
```

解析顺序：

| 顺序 | 匹配源 | 命中后的 `quote_resolution` |
|---|---|---|
| 1 | `listening_messages`（人类，原有） | `matched_one_original_transport_message_in_this_group` |
| 2 | `listening_assistant_context`（机器人） | **`quoted_bot_own_message`**（新增） |
| 3 | 都未命中 / 多命中 | `unverified_quote_not_original_member_evidence` |

约束：

- **必须唯一命中**，多命中视为歧义，不触发。
- 匹配键仍是 `sender_id + text` 全等。
- `quote["complete"]` 为假（微信截断）时不匹配。
- 命中后设 `reply_to_id` 为机器人消息 ID，并新增派生字段 `addressing_bot = True`。

### 1B 引用机器人即触发

```
explicit = message.mentioned
           or 任一关键词（"小温暖"/"小溫暖"）
           or payload.get("quote_resolution") == "quoted_bot_own_message"
```

`explicit` 天然绕过随机概率与冷却，语义与其他明确呼叫一致。

### 1.3 幂等性影响

`fingerprint = digest(canonical)`，`canonical` 只含 `platform_id/bot_id/group_id/sender_id/sender_name/message_id/sent_at/text/mentioned`。新增的 `quote_resolution` / `addressing_bot` 都是 `payload` 字段，**不进 `canonical`，不影响指纹与"同 ID 内容冲突"判定**。

### 1.4 提示词侧

`group_prompt.render_group_policy()` 在 `addressing_bot` 为真时追加：

> 本轮对方是在回应你刚才说过的话。你上一句的内容已经在历史里，不要复述它、不要重新解释一遍，直接接住对方的意思再往下说。

**不复述原文**，避免模型自我引用。机器人历史仍只作"生成记录"，不作人类证据。

### 1.5 改动清单

| 文件 | 改动 |
|---|---|
| `src/myatri_bridge/short_memory.py` | 新增 `recent_assistant()` |
| `src/myatri_bridge/bridge.py` | 引用解析加一路 + `explicit` 加一项 |
| `src/myatri_bridge/context.py` | `identity_source` 透传 `addressing_bot` / `quote_resolution` |
| `src/myatri_bridge/group_prompt.py` | 新增"被回应"提示块 + `derived.current_addresses_bot` |
| `tests/test_quote_addressing.py` | 7 条定向测试 |

### 1.6 测试点（全部通过）

引用机器人命中并触发；截断引用不命中；引用人类走原路径；歧义不触发；重试指纹不变；冷却被绕过；机器人不计入人类证据；提示词含/不含该规则。

# 方向 2：接入 DeepSeek Harness 实现联网　✅ 已实现（默认关闭）

## 2.1 事实基线（实测，非推测）

| 事实 | 依据 |
|---|---|
| DSH 开源，loader 架构"一切皆插件" | 公开仓库 |
| profile = bundles + patch 层 | `~/.dsh/profiles/desktop/package.json` |
| Agent 由 preset 定义（`agent.cordis.yml` + `.mjs` 工具） | `~/.dsh/.agent-presets/*/` |
| 权限预设 read-only / workspace-write / danger-full-access，**桌面端默认 `danger-full-access` + `approval: never`** | `~/.dsh/profiles/desktop/cordis.patch.yml` |
| 本机 CLI：`~/.dsh/profiles/node_modules/@deepseek-ai/dsh/lib/bin.js`（`0.1.2-alpha.1`） | 本机实测 |
| 调用：`dsh --profile headless "<task>"`，本机版本只接受位置参数 | 读 `lib/bin.js` + 实跑 `--help` |
| stdout 只输出最终回答；reasoning 走 stderr；退出码 0 = 完成 | 同上 |
| **无头默认沙箱是 `workspace-write`**，`tool-web` 只开搜索、无网页抓取 | `--dump-config` 实测 |
| 模型 `deepseek-v4-flash`，**每次搜索都是一次计费请求** | 同上 |

## 2.2 架构选择：进程外子代理

```
mytri 工具循环
   └─ web_search(query)  ← 注册在 conversation.tool_handlers
        └─ 子线程：dsh（无头）→ 专用只读 preset
             └─ stdout JSON → 解析 → 截断 → 作为 tool 结果注入
```

理由：崩溃不连累桥接；权限边界由独立 profile 强制；与既有 `tool_handlers` 接缝一致。

## 2.3 三层隔离

| 层 | 做法 |
|---|---|
| 权限 | 客户端强制 `DSH_PERMISSION_MODE=read-only`，拒绝构造 `danger-full-access` |
| 工作目录 | `var/agents/websearch/`，不指向项目仓库，不含 `AGENTS.md` 与凭据 |
| 输入 | 只含查询词组，绝不拼接群聊原文、角色卡或凭据；环境变量白名单化，强删 `*_KEY/*_TOKEN/*PROXY*` |

## 2.4 工具契约

```jsonc
{"type":"object",
 "properties":{
   "query":{"type":"string","maxLength":200},
   "max_results":{"type":"integer","minimum":1,"maximum":5},
   "recency_days":{"type":"integer","minimum":1,"maximum":30}},
 "required":["query"],"additionalProperties":false}
```

返回按既有 `TOOL_BYTES = 6000` 截断。失败码：`search_timeout` / `search_backend_failed` / `search_output_invalid` / `search_quota_exhausted`，**任何一条都不得编造内容**。

## 2.5 触发策略

| 路径 | 何时 | 延迟预算 |
|---|---|---|
| 前台按需 | 命中意图词或明确要求 | 超时 25 秒，超时降级 |
| 后台预取 | 摘要轮批量搜群聊提及话题，结果落缓存 | 不占聊天延迟 |

## 2.6 缓存与审计

每群独立 `web.sqlite3`：`web_cache(query_hash, payload, fetched_at)`，TTL 24 小时；日限额 40 次。审计只记 `{query_hash, duration_ms, result_count, cached, truncated, error}`，**不记原文**。

## 2.7 改动清单

| 文件 | 改动 |
|---|---|
| `src/myatri_bridge/dsh_client.py` | 子进程封装：固定 argv、`shell=False`、超时 kill、环境白名单、目录隔离 |
| `src/myatri_bridge/web_tools.py` | `WEB_SEARCH_TOOL` + `DshBackend` + `WebSearch`（缓存/日限额/审计）+ 6000 字节截断 |
| `src/myatri_bridge/reading_conversation.py` | **支持 awaitable 工具处理器**（修复原同步派发会阻塞事件循环的缺陷） |
| `src/myatri_bridge/bridge.py` | 注册 `web_search`，用 `asyncio.to_thread` 跑子进程；未开启时不建文件 |
| `config/bridge.example.toml` | `[bridge.web]`，默认 `enabled = false` |
| `tests/test_web_tools.py` / `test_web_wiring.py` | 49 + 3 条 |

## 2.8 风险

| 风险 | 处置 |
|---|---|
| 子进程带默认全权限 | 强制只读，启动校验 |
| 提示注入导致不当发言 | 工具只读、内容标记为材料、回复带来源 |

# 方向 3：自发起话题（3B）　🟡 基础设施完成

## 3.1 三个硬约束

| 约束 | 位置 | 影响 |
|---|---|---|
| 引擎硬封锁 | `src/myatri/app.py:39-40` —— `outreach.enabled` 为真直接 `raise` | 打开配置会崩 |
| `respond()` 强制写用户消息 | `conversation/engine.py` `append_message("user", ...)` | 主动轮没有 user 文本可写 |
| 平台原本无主动发送能力 | `wechatagent_platform.py` 未实现 `send_by_session` | 已补 |

回执验证在 `NativeClient.send()` 内，**不依赖事件对象**，可直接复用。

## 3.2 核心设计原则：不伪造人类证据

采用 `turn_kind` 维度，而非新造并行链路：

| 字段 | 取值 | 含义 |
|---|---|---|
| `record_kind` | `raw_message` | 不变 |
| `author_kind` | `self_initiated` | 明确"这不是人类说的" |
| `reality_scope` | `internal` | 内部指令，不来自真实渠道 |
| `payload.self_initiated` | `true` | 桥接侧过滤依据 |

## 3.3 引擎侧最小改动（源码已改，未安装）

`append_message` 增加关键字-only `author_kind: str | None = None`（默认行为不变，显式值做契约校验）；`Conversation.respond` 透传。**改动 ~40 行，全量 353 测试通过。**

> **已解除（采用方案 B）**：`.venv` 安装的 wheel `0.2.8` 不支持 `author_kind`，因此主动轮**完全不写 `role="user"` 记录**——指令只作为该次请求的 system 消息，不落盘为 `raw_message`；只有确认发送后的回答经 `acknowledge()` 以 `role="assistant"` 入档。
> 这样既不依赖引擎改动，也不触碰任何 `role == "user"` 的证据门槛。引擎侧的 `author_kind` 透传仍保留在源码中，作为将来可选的正规化路径。

## 3.4 三阶段

| 阶段 | 内容 | 是否对外发送 | 状态 |
|---|---|---|---|
| 阶段 1 影子 | 照常判定与生成，**只落草稿不发送** | ❌ | ✅ 已实现（`shadow_mode` 默认 true） |
| 阶段 2 通道 | 平台 `send_by_session` + 插件轮询 + 复用投递状态机 | ✅ 手动 | ✅ 已实现 |
| 阶段 3 开启 | 打开调度器与限额 | ✅ 自动 | ✅ 已实现（默认 `enabled=false`，需显式打开） |

## 3.5 调度器

`ProactiveScheduler`（`src/myatri_bridge/proactive.py`，依赖注入、可冻结时钟）由 `Bridge._ensure_proactive()` 按 scope 创建，随 `start()` 与首个消息启动，`close()` 取消。

拍板间隔：截断指数分布 20–90 分钟。

## 3.6 闸门（顺序短路）

| # | 闸门 | 取值 |
|---|---|---|
| 1 | kill switch | `var/KILL_PROACTIVE` 存在即停 |
| 2 | 全局开关 | `enabled`，默认 false |
| 3 | 活跃时段 | 09:00–23:30 |
| 4 | 距上次发言 | ≥ 15 分钟 |
| 5 | 当日主动发言 | ≤ **10** 条 |
| 6 | 群内静默 | > 2 小时跳过 |
| 7 | 预算余量 | 当日已用 < 80% |
| 8 | 候选 TTL | 45 秒 |

**沉默优先**：任一环不确定就跳过，不重试不补偿。

## 3.7 候选选择

| 优先级 | 候选 | 状态 |
|---|---|---|
| 1 | 明确呼叫但生成失败 | ✅ 已接 |
| 2 | 被判为不该回但话题未闭合 | 预留 |
| 3 | 临时状态池的念头 | 预留 |
| 4 | 最近没人接的问句 | ✅ 已接 |

候选若带主动标记 → 判 `candidate_source_polluted`，绝不自产自销。

## 3.8 发送通道

```
插件 initialize() 启动后台任务（proactive_enabled=true 才启动）
  └─ 每 10 秒 GET /v1/deliveries/pending?scope=
       └─ POST claim → context.send_message → 逐段 ack{part_index}
```

平台侧 `send_by_session()` 先 `native.check()` 再 `native.send()`，复用 5 条件回执验证；`support_proactive_message=True`。

投递语义完全复用现有状态机；`unknown` 永不自动重投。

# 四、与既有原则的一致性

| 项目不变量 | 本设计如何保持 |
|---|---|
| U01 事件与解释双轨 | 1A 只加派生字段，不改原话 |
| U05 人格变化可回忆 | 主动发言记录候选与原因，可回查 |
| U06 前后台一致性 | 3B 走同一提交路径 |
| 机器人输出不是人类证据 | `author_kind` + 1A 明确区分来源；生成路径在引擎不支持时直接拒答 |

| 外部内容不是指令 | 2 的网页内容一律标记为材料 |
