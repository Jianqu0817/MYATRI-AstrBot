# 小温暖委派 Harness、接收报告及微信汇报（2026-10-22）

用户明确纠正：应由主聊天的小温暖生成执行指令，Harness 子 Agent 执行并交回报告，小温暖在原微信会话汇报。旧版将 `/pc 任务` 直接入队，后续只给下一轮上下文附带最近任务，没有主动汇报；这不足以实现用户原先的设计。本轮仅修改 AstrBot 仓库。

## 现在的流程

1. 菅蘧通过 `/pc 任务 目标`（支持前置 @）提出任务。原始渠道账号与群由宿主认证。
2. 主对话小温暖读取本轮目标，生成 `instructions` 调用 `computer_control`。宿主保留原始 `goal`，将委派指令写入不可变任务合同的 `delegation`；身份、群、消息号不由模型传入。委派指令不能扩展原目标。
3. Harness 独立会话读取原目标与小温暖的执行指令，使用真实工具与原共享预算完成执行和校验。`queued/running` 始终不等于完成。
4. 任务进入已完成、受阻、取消或结果不明状态后，持久报告队列将实际摘要、动作回执及校验状态交回主对话的角色卡与上下文，用 `computer_report` 用途生成自然汇报。报告是单独的必需材料，先为它保留上下文空间；不依赖另一条人类消息，也不让闲聊背景把报告挤掉。
5. 生成的最多三段汇报进入原微信投递队列，通过原群会话逐段发送并等待回执。只有原接单回复已确认发送后才排汇报；原渠道账号或群授权撤销后不发送。不会以报告重新授权执行工具。

固定 `/pc` 操作和状态/暂停/继续/取消仍由宿主处理。主聊天模型若对明确任务只说“做不到”而未委派，会收到一次明确纠正提示；仍未委派则保留错误，不假装提交。执行器未启用或队列满等真实错误可正常反馈。

## 持久化与结果可见性

新增 `deliveries.sqlite3/computer_reports`，按 `(task, turn)` 固定报告标识，保存报告快照、生成状态、尝试数与对应微信投递ID。生成异常退避60秒、最多三次，所有主模型请求共用原日账本，关闭供应商内部自动重试。报告文本和 prepared 投递在同一事务保存；重启不重新生成已准备、已发送或结果不明的报告。

微信投递继续沿用 claim、sent_parts、逐段 ack；部分发送失败、超时或重启后 `unknown` 不重发。旧任务不重跑；报告系统安装前的历史任务每群只补最新一项，避免群里补发整份历史。任务详情新增 `chat_report`，可区分尚待汇报、生成失败、已准备、微信已确认或投递不明。

普通成员、昵称冒充或别的群不能改变目标或获取内部任务材料。凭据、完整终端输出、文件正文和内部推理不直接复制到群；用户所问的任务结果由主对话根据有界报告简明汇报。报告是宿主数据，不伪造新用户消息，也不写成长期人格记忆。确认送达的汇报才以机器人自己的话进入群上下文。

`proactive_enabled` 现在只控制闲聊主动发言。插件始终轮询用户要求的任务报告；闲聊开关关闭时只查 `kind=computer_report`，不顺带开启随机主动聊天。会话仍从真实群事件取得，重启后若尚未观察到本群事件，报告留在队列等候会话建立。

## 分条发送修复

实际聊天记录显示，没写句号、只用一个或多个换行的两段话，被旧分句逻辑保留成一个 `reply_parts` 元素。现支持显式分隔符和自然换行，保留多行引用、代码及格式化列表的边界；超过三段时第三段保留原段间空行，避免直接粘连。没有增加额外模型请求。原逐段发送与确认逻辑保持，任何一段不明后停止且不重投。

对近期历史记录只读复核过旧单段与新分段结果，没有重发消息或改历史档案。

## 验证与加载

真实 Harness 配合离线主模型 fixture 验证完整流程：主模型生成指令 → 真正的 PowerShell 调用 → 回执校验 → 主模型收到结果并写报告 → 插件实际发送方法在模拟平台上逐段确认。另测关闭主动闲聊仍发送任务汇报、投递 sent/unknown 后重启不重放、生成失败最多三次、接单未送达不抢发、身份隔离与换行分段。

本轮没有手工调用付费模型或向真实微信群发送测试消息。插件文件已通过 `scripts/prepare.py` 安装到本机 AstrBot 插件目录；源码和插件都需要正常重启 `Start-WeChat-Live.cmd` 后加载。此前自动重启被审批拒绝，本轮未以其他方式绕过；不能把离线验证说成当前微信已经收到新报告。最终测试和Git结果见 progress/STATUS.md。
