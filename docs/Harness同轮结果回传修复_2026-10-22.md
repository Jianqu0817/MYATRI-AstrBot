# Harness 结果回到小温暖原对话（2026-10-22）

本次仅修改 MYATRI-AstrBot。用户要求的链路是：小温暖生成执行指令，Harness 执行并返回结果，小温暖读取结果后再回复。此前虽然报告请求使用相同角色卡，却是另一次独立的模型请求，原对话拿到的仍只是 queued/task_id，不能保证两次回答一致。

## 现场核对

只读核对投递及任务记录发现：13:25 提交的内存任务已经完成，其独立报告在 14:06 才发送；随后一条新的“@小溫暖 帮我查询内存容量空间”没有创建任务，主对话回复不能访问电脑。后一条请求没有 `/pc` 前缀，旧身份门控将它和普通聊天一起排除在电脑工具外。旧结果和新拒绝属于不同原始消息，不应当被解释为同一条查询的两次正常回复。

## 当前流程

1. 宿主按当前真实人类消息的稳定账号及允许群核验权限，仅菅蘧可取得电脑工具。自然语言请求也可以使用；普通闲聊无需调用，引用或历史里的账号不能授权其他成员。
2. 小温暖单独调用 `computer_control(instructions=...)`。执行目标、群和任务去重 ID 仍由原始信封固定。对明确 `/pc 任务` 和直接硬件查询若先回答不能操作，最多进行一次纠正。
3. 执行前持久保存当前 assistant tool_call、工具调用 ID、执行指令及待返回的 tool 位置，再登记原始投递等待状态并提交任务。当前对话返回内部 `waiting_for_computer`，插件不向用户发送这项内部状态。
4. 等待期间释放群与对话锁，状态和停止控制可以继续使用，主动闲聊调度不会抢答等待中的请求。
5. Harness 完成、受阻、取消、暂停或结果不明后，后台续接器恢复原消息的协议。原调用的 tool 消息替换为真实任务状态、结果摘要、执行时间及有界回执反馈，小温暖从这里继续生成最终回答。任务 ID、tool_call_id、原始用户消息和投递 ID 全部保持对应。
6. 最终回答使用正常对话的回复检查、分段及持久投递机制，由微信插件逐段发送和确认。不会为报告再创建 `purpose=computer_report` 的独立聊天请求，也不先发送模型接单回复。

`computer_reporting.py` 现在负责续接原对话，不自行组装另一个角色请求。`kind=computer_report` 仍是投递队列过滤标识，供关闭主动闲聊的插件接收任务结果；它不代表新增模型对话。报告留在本轮工具协议和任务库，最终回复进入正常助手历史，不冒充人类证据。

## 恢复和边界

任务仍按原消息固定 ID 去重，恢复工具调用只读取已有任务状态，不重新执行已完成或不明的操作。提交前后中断均可根据工具检查点和等待登记续接；生成结果时中断则从原轮恢复。正常状态查询和固定 `/pc` 操作保留原宿主处理路径。

报告生成失败采用最多三次、60 秒退避，共用原主对话账本及供应商策略，不重跑执行器。已经准备的最终回复可由原队列领取；已发送或投递不明不重发。清空或重载上下文会淘汰还在等待的旧回复。

升级时只将尚未发送的旧 `pc_report_` 独立草稿标为 superseded，保留正文、已发送与 unknown 记录。不补发历史任务，不改旧任务的实际状态或结果，不重放真实电脑操作。

## 验证与加载

使用离线模型 fixture 和真正安装的 Harness/PowerShell 验证命令与自然语言两条完整链路：主对话委派 → 实际工具执行及校验 → 原 tool_call_id 收到真实结果 → 同一轮主对话最终回复 → 插件实际发送方法逐段确认。另覆盖暂停/失败/不明结果、等待中控制、任务提交前后中断、重启去重、旧草稿迁移和关闭主动闲聊时的任务投递。

本次不手工调用付费模型、不向真实微信群发送测试消息，不修改相邻核心或角色卡。桥接服务需要正常重启才能加载 Python 源码；微信插件协议没有变化。最终回归结果见 `progress/STATUS.md`。
