## 三、要解决的问题

### P0-1 旁听摘要零成功，长期记忆无法写入

**现象**：`listening_summaries = 0`。537 条消息产生 5 个待办窗口，全部反复重试失败，退避时长已累积到最长 22 小时之后。

**证据**：

| 窗口 | 已试次数 | 失败阶段 | 失败码 | 请求上限 |
|---|---|---|---|---|
| 1–100 | 6 | generate | `output_length` | 8000 |
| 101–200 | 5 | validate | `evidence_validation` | — |
| 201–300 | 4 | validate | `evidence_validation` | — |
| 301–400 | 3 | generate | `output_length` | **12000** |
| 401–500 | 3 | generate | `invalid_schema` | 8000 |

每个窗口输入约 21 KB（约 7 千汉字）。用量表 `purpose=group_short_memory` 共 21 次调用，0 次成功。

**根因**（`src/matri_bridge/short_memory.py`）：

1. **容量设计不足**：一次性对 100 条消息生成摘要，并要求逐条给出逐字证据，输出需求超过 12000 tokens。窗口 301–400 在 12000 下仍然截断，说明不是调大上限就能解决。
2. **失败链条**：截断 → JSON 不完整（`invalid_schema`）；勉强完整 → 引文或主体对不上原文（`evidence_validation`）。
3. 代码位置：`short_memory.py:23` `SUMMARY_MAX_TOKENS = 8000`、`:24` `SUMMARY_REPAIR_MAX_TOKENS = 12000`、`:331` `summarize_pending`、`:303` `_validate_items`。

**后果**：启动至今没有一条新的长期记忆写入。当前回复只依赖最近 100 条窗口、800 条冷档检索、以及 0.1.2 迁入的旧历史；`SummaryArchive → event / interpretation` 的升格链路从未跑通。

**建议**：
- 把摘要窗口从 100 条改为 25–50 条分块汇总，再对分块结果做一次归并；或把"逐字证据"改为按消息 ID 引用区间，避免逐条复制原文。
- 同时保留现有退避与 `listening_pending` 的输入冻结机制（这部分设计是对的，不需要改）。

**验收标准**：真实积压的 5 个窗口能产出 `listening_summaries ≥ 1`，且 `listening_pending` 清空；用现存的 21 KB 待办回放验证，而不是只跑 fixture。

### P0-2 摘要的 token 升额逻辑失效

**现象**：窗口 1–100 已试 6 次，失败码为 `output_length`，但记录的请求上限仍是 8000，从未升到 12000。

**根因**（`short_memory.py:362`）：

```python
if previous_error.get("code") == "output_length":
    max_tokens = SUMMARY_REPAIR_MAX_TOKENS
```

只在"紧邻上一次错误恰好是 `output_length`"时才升额。当错误码在 `output_length` / `invalid_schema` 之间摆动时，升额永远踩不中。

**建议**：改为"最近 N 次中只要出现过 `output_length` 就升额"，或按尝试次数单调递增。

### P1-1 A1 长期事实提炼被成员 ID 校验永久拒绝

**现象**：`jobs` 表中 `maintenance` 任务连续尝试 3 次后 `failed`，错误为
`ValueError: group memory participants must be real known member IDs`。

**判断**：校验本身是对的——模型编造了不存在的成员 ID，拒绝是正确的。但当前策略是**整批拒绝**，导致只要模型偶尔编一个 ID，整批真实事实全部作废，实际效果等于永久不产出。

**建议**：把未知 ID 过滤并记录下来（降级为未确认归属），而不是整批失败；同时对连续失败的批次给出可见告警。

### P2-1 `seen_messages` 与 `listening_seen` 相差 17 条

**现象**：`seen_messages = 520`，`listening_seen = 537`。

**含义**：这两个计数写在不同数据库、不同事务中，进程在两次写之间中断会产生缺口；也可能 `scripts/backfill_group_memory.py` 只补了一侧。无论哪种，都意味着有 17 条消息在桥接层没有留下去重记录，理论上存在重复处理风险。

**建议**：先确认这 17 条的来源（比对消息 ID），再决定是补写还是接受为崩溃窗口遗留。

### P2-2 关键指标没有告警

`GET /v1/diagnostics` 从服务启动第一小时起就返回 `short_summaries: 0` 和 5 条带 `attempts` 的待办，但无人发现。

**建议**：为 `short_summaries == 0 且 pending > 0`、`pending.attempts ≥ 3`、`unknown 比例 > 20%` 设置阈值检查。本次问题本可一眼可见。

### 观察项（暂不列为待办）投递失败率 24%

`sent 197 / unknown 63 / superseded 2`。

- 状态机本身正确：无 `sending` / `prepared` / `received` 残留，`sent` 与分段数完全一致，63 条中 15 条是"部分段落已发后失败"且如实记为 `unknown`，未伪装成 `sent`。
- 失败集中在 17 时（16 条）与 18 时（11 条），与发送高峰同步；低峰时段每小时仅 2–7 条。**与吞吐量正相关，不像持续性故障**，最可能是回执 18 秒超时在高负载下被踩中。
- 建议先观察一天，确认是否与并发量相关，再决定调整回执超时或串行发送策略。
